# 「DNS浸透」を「見て」みよう

「DNS浸透」は、設定変更がインターネット全体へ少しずつ広がるかのような誤解を招く表現です。この Web ツールでは、DNS とブラウザーのキャッシュを操作しながら、古い応答がキャッシュの有効期間中に使われ、期限切れ後の問い合わせで改めて取得される様子を学べます。

次の 3 つのシナリオを切り替えて、アクセス結果やキャッシュの残り時間、問い合わせの流れを確認できます。

- **Web サーバーの IP アドレスの変更**: 同じ権威サーバー上の A / AAAA リソースレコードを新しい IP アドレスに更新します。
- **権威サーバーの移転**: 親ゾーンの NS リソースレコードを変更し、新しい権威サーバーに委任します。変更前の委任情報をキャッシュしているフルサービスリゾルバーは、期限が切れるまで旧サーバーを使うことがあります。
- **ネガティブキャッシュ**: A / AAAA リソースレコードを追加する前にアクセスし、NXDOMAIN 応答がフルサービスリゾルバーにキャッシュされる様子を確認します。レコード追加後もキャッシュの有効期間中は NXDOMAIN が返り、期限切れ後の問い合わせで追加したレコードが取得されます。

これはブラウザー内で完結する**シミュレーション**です。実際の DNS サーバーへの問い合わせや設定の変更は行いません。

## 起動

Node.js 18 以降が必要です。外部パッケージのインストールやビルドは不要です。FreeBSD では、必要に応じて Node.js と npm をパッケージからインストールしてください。

```sh
pkg install node npm
npm start
```

既定では `127.0.0.1:3000` で HTTP を待ち受けます。変更する場合は `HOST` と `PORT` を指定します。

```sh
HOST=127.0.0.1 PORT=3000 npm start
```

ブラウザーで `http://127.0.0.1:3000/` にアクセスします。別ホストから公開する場合は Node.js をループバックで待ち受けさせ、別途用意した Nginx で HTTPS を終端してください。例えば、証明書とドメインを用意したうえで、Nginx の HTTPS `server` ブロックに以下を設定します。

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

## 使い方

1. シナリオとレコードタイプを選び、「サイトにアクセス」で各キャッシュを作ります。
2. 「設定を変更する」または「A / AAAA レコードを追加する」を押して再度アクセスすると、古いキャッシュが使われる様子を確認できます。
3. 時間を進めてアクセスを繰り返します。「HTTP キャッシュのみ消去」でブラウザーの DNS キャッシュを、「ブラウザーのキャッシュを消去」でフルサービスリゾルバーのキャッシュを確認できます。リセットすると選択中のシナリオを最初から試せます。

ブラウザーとフルサービスリゾルバーのパネルでは、キャッシュの残り時間、期限切れ、未保存・消去後の「なし」を確認できます。「サイトにアクセス」を押すと、実際に使ったキャッシュの行にオレンジの印が付きます。HTTP キャッシュで表示できた場合は、名前解決結果が期限切れでも HTTP の行だけに印が付きます。プレビューの枠は表示するページ自体が変わったときだけ強調します。設定の変更結果は権威サーバーのパネルで確認できます。

アクティビティでは、権威サーバーの DNS 応答、フルサービスリゾルバーのキャッシュ保存と応答の返却、ブラウザーのキャッシュ保存とページ取得を、処理主体ごとに表示します。IP アドレス変更では同じ権威サーバーを使い、移転では実際に問い合わせた委任先を「旧権威サーバー」または「新権威サーバー」と表示します。

デモでは IP アドレスのリソースレコードの TTL を 120 秒、委任情報を 180 秒、ネガティブキャッシュを 120 秒、ブラウザーの DNS キャッシュを 30 秒、HTTP キャッシュを 90 秒に固定しています。ネガティブキャッシュの TTL は SOA 情報から算出されますが、このデモでは 120 秒として簡略化しています。また、ネガティブキャッシュのシナリオではフルサービスリゾルバーの NXDOMAIN キャッシュのみをモデル化し、ブラウザー側の失敗結果キャッシュは扱いません。ブラウザー DNS キャッシュの 30 秒は、フルサービスリゾルバーから受け取った応答の残り TTL にかかわらず適用する簡略モデルです。そのため、リゾルバーのキャッシュ期限が近いタイミングで応答を受け取ると、ブラウザー側の DNS キャッシュがリゾルバー側の期限を越えて残る場合があります。ただし、現在のデモでは時間を 30 秒の倍数で進めるため、このケースは画面操作では再現できません。HTTP キャッシュが有効な間は DNS 問い合わせを行いません。権威サーバー移転のシナリオでは、旧サーバーが古い応答を返し続ける場合をモデル化しています。古い委任情報を使って再取得した IP アドレスは、委任情報の期限が切れた後も自身の TTL まで残ります。このシナリオは NS リソースレコードによる委任とグルーレコードを 1 つの委任キャッシュとして簡略化しており、グルーレコードの個別の更新・TTL は再現しません。実運用では移転前に新サーバーのゾーンデータを整え、旧・新サーバーが同じ応答を返す期間を設けるのが重要です。

実際のブラウザーやフルサービスリゾルバーのキャッシュ、接続再利用、TTL の扱いは実装や設定によって異なります。このデモは DNS のすべての挙動を再現するものではありません。移転時には旧・新サーバーのデータの整合性や、親ゾーンの委任・グルーレコードも考慮してください。

DNS 用語は [JPRS 用語辞典](https://jprs.jp/glossary/) と [RFC 9499: DNS Terminology](https://www.rfc-editor.org/rfc/rfc9499.html) を参考にしています。
